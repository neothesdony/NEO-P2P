# CRITICAL — Known Structural Issues in NEO-P2P

> **TL;DR**: We generate one Ed25519 key in StrongBox and then lie to five different protocols about what kind of key it is.

Generated by Prism Full (adversarial multi-pass structural audit) on 2026-05-30.
Read this before touching identity, crypto, escrow, or reputation code.

---

## The Single Point of Total Failure

NEO-P2P's identity layer is **cryptographically invalid**. We store a single Ed25519 keypair in
Android KeyStore, then derive all protocol identities from it via SHA-256:

| Protocol | Required Key Type | What We Give It | Works? |
|----------|------------------|-----------------|--------|
| Nostr (NIP-01) | secp256k1 Schnorr | SHA-256(Ed25519 pubkey) | **No** |
| Lightning Network | secp256k1 ECDSA | SHA-256(Ed25519 pubkey) | **No** |
| libp2p PeerID | Ed25519 or secp256k1 | SHA-256(Ed25519 pubkey) as PeerID string | **Fake PeerID** |
| Signal Protocol | Curve25519 (X25519) | Separate in-memory key (lost on restart) | **Yes, but not persisted** |

**Consequence**: Nostr events are unsigned garbage, Lightning transactions cannot be built,
libp2p PeerIDs are synthetically generated strings with no cryptographic binding to the key,
and Signal sessions evaporate on app restart.

**Privacy consequence**: All protocol identities are SHA-256 of the same Ed25519 public key.
Anyone who sees your Nostr npub and libp2p PeerID can trivially correlate them.

## Identity Rewrite Blueprint

See `IDENTITY_REWRITE.md` for the full architectural plan.

**Core approach**: Replace single Ed25519 KeyStore key with BIP-39 + BIP-32 seed model.

```
seed (BIP-39, 128-bit entropy + checksum)
  ├── m/44'/1237'/0'/0/0  → nostrKey      (secp256k1)
  ├── m/44'/0'/0'/0/0     → lightningKey  (secp256k1, BIP-44 Bitcoin)
  ├── m/44'/888'/0'/0/0   → libp2pKey     (Ed25519)
  └── m/44'/999'/0'/0/0   → signalKey     (Curve25519)
```

Seed encrypted with KeyStore-wrapped AES-GCM. Derivable keys stay in memory.
Backup = BIP-39 mnemonic. Restore = validate checksum, derive all keys from path.

## What's Actually Good

This audit is harsh because the bar is high. The things that work are genuinely solid:

- **Infrastructure**: 4× strfry Nostr relays + 1× libp2p circuit relay + 1× coturn TURN on Oracle Cloud Free Tier. Deploy scripts are clean. Docker compose is well-structured.
- **UI**: 8 Compose screens with Material 3 dark theme. Navigation graph, Hilt DI, ViewModels all correct.
- **P2P transport**: java-libp2p host configuration is sensible (AutoRelay, circuit relay, WebSocket + TCP transports).
- **Identity concept**: KeyStore StrongBox integration for the master key is correct. Just needs to be the *seed* key, not the *only* key.
- **Project structure**: Clean separation of concerns. Domain models, repositories, use cases, data sources. Good Kotlin patterns.
